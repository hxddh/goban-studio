# 围棋 App 可行性评估

> 本文写于开发之前，描述的不是现在的应用。现在的应用见仓库根目录的 [README](../README.md) 和 `docs/QA.md`。

> 这是开发前的评估文档（2026-11-01）。实现进度、已验证范围与未验证边界见仓库根目录的 `README.md` 和 `docs/QA.md`；本文件保留当时的架构与工期判断，不随实现自动更新。

**参照仓库**：[hxddh/chessboard](https://github.com/hxddh/chessboard) `main @ 2558785`（v17.0.0）
**对照仓库**：[hxddh/goban](https://github.com/hxddh/goban)（五子棋，v3.2.0）
**评估日期**：2026-11-01
**评估问题**：能否充分利用 chessboard 的架构思路和代码，做一款围棋 App？

---

## 0. 结论

**可行，推荐做；但不能把 chessboard 原地改成围棋。**

分层看复用率：

| 维度 | 复用度 | 说明 |
|---|---:|---|
| **架构思路** | **80–90%** | 原生壳 + WebView + Canvas、单 bundle、三切片 store、原生文件镜像存档、内容按 id×locale、构建期守卫、双引擎 E2E——这些都与棋种无关 |
| **代码直接复用** | **约 30%** | 原生壳、文件桥、存档、棋谱库、SRS、进度/成就、UI 设计系统、i18n 基础设施、构建/CI/打包 |
| **代码改造后复用** | **约 25%** | 复盘 UI、训练框架、棋谱树、音频、统计、设置、菜单 |
| **必须新写** | **约 45%** | 围棋规则、棋盘几何、SGF、引擎适配、围棋复盘指标、全部围棋内容 |
| **内容** | **0%（全部新做）** | 课程、死活题、手筋、定式、官子、名局、翻译；这是总工作量的一半以上（四语更多） |

**一句话判断**：chessboard 是一套已经被验证过两次的“棋类应用操作系统”。围棋要换的是**规则、引擎、内容和棋盘几何**，不是壳。

**五个关键判断**：

1. **最大技术风险是围棋 AI，不是规则或棋盘。** Stockfish 是 1.8 MB 的单线程 wasm、UCI 协议、1,300–3,500 Elo 的连续限强；围棋需要 KataGo 这类 MCTS+神经网络引擎，模型从约 5 MB 到 271 MB，且没有等价的 `UCI_Elo`。这是全项目唯一需要先做 spike 的地方。
2. **最大工期风险是内容，不是代码。** chessboard 的 10.5 万行 JS 里约 58% 是棋种内容/数据（课程、4 万道 Lichess 题、ECO、名局、残局、三语翻译）。这些对围棋一行都用不上；围棋的课程、死活题、定式、棋谱要重新生产并逐条验证。
3. **最佳首发形态是桌面（macOS/Windows）+ 9/13/19 路 + 入门教学**，不是移动端。仓库在 v1.2.0 时的 `docs/MOBILE-EVAL.md` 结论也是：Native SDK 移动端当时仍是 experimental，先做可玩性 spike，不进商店（该评估较早，移动端现状需重新核实）。
4. **四语（中/英/韩/日）是第四份内容，不是第四本字典。** chessboard 现有 1,431 个 UI 键、每语言 2,019 条教学内容；韩语要新增约 3,450 条字符串，四语本地化（UI + 内容 + 母语审校）约 **10–12 人周**。UI 四语应从第一天做（详见 §10）。
5. **不拆公开版本，只发一个完整 v1.0。** P0–P5 是内部工作流，不是版本；内容、四语、QA 必须在发布前全部完成。按这个要求重算，工作量 **57–72 人周**：3–4 人团队约 **8–9 个月**，单人约 **13–17 个月**。上一版的“5.5–8 个月”是按分阶段/首发内容估的，不适用于“一次完成产品化”（详见 §7、§11）。

**推荐路线**：新开一个 **`goban-studio`** 仓库（不改现有五子棋仓库 `goban`；命名理由见 §10）——

- 从 **chessboard** 取：原生壳、构建/测试/CI、持久化、棋谱库、复盘/训练框架、设计系统、四语 i18n 基础设施；
- 从 **goban** 取：交叉点棋盘渲染、石子质感、落子音效、SGF 的起点；
- 从 **Sabaki 的 MIT 库**取：围棋规则、SGF 解析、棋谱树、GTP；
- 新写：围棋规则封装与数目、KataGo 适配、围棋复盘指标、全部围棋内容。

不要做的三件事：不要把 `app.js`（4,816 行、约 50 个 import）整体改造成围棋；不要试图复用 `chess.js`/`fide.js`/PGN/ECO/Stockfish；不要先做移动端或 19 路满强度 AI。

## 1. 关键证据

### 1.1 这套架构已经跨棋种复用成功过一次

这不是推测，是仓库历史里写着的：

- chessboard 的 **v0.1.0**（commit `632ad60`）提交信息：

  > “Bootstrapped from the goban (gomoku) architecture: Native SDK shell (main.zig/runner/build.zig renamed, bridge commands chess.*), host/audio modules, styles, dual-platform CI (build-macos/build-windows/release) and the packaging script — all adapted.”

- chessboard 的 **v0.4.0**（commit `acd1bdb`）标题是「**去围棋化整改**」：早期界面沿用了围棋/五子棋的「手」、圆子、○/△ 记号，这一版才改成国际象棋的「着」、王字形、呢绒木子音效。

也就是说：

- 这套壳已经服务过**五子棋**和**国际象棋**两个棋种；
- chessboard 自己就是从 goban 的架构上长出来的；
- 围棋会是这套架构的**第三次复用**，不是从零验证。

### 1.2 代码体量与构成（实测）

| 项 | 数值 | 说明 |
|---|---:|---|
| Web JS | **105,199 行** | `src/web/js/**/*.js` |
| 其中内容/数据 | **61,319 行（58.1%）** | lessons / puzzles / lichess / eco / classics / endgames / openings / i18n 翻译等（按文件归类粗算） |
| 其中代码 | **43,880 行（41.9%）** | 壳、状态、持久化、棋谱库、复盘、训练、UI、引擎 |
| Zig 原生层 | **6,559 行** | `src/*.zig`（含 fork 的 runner/build） |
| CSS | **4,944 行** | 设计 token、四套主题、组件 |
| HTML | **1,638 行** | 单页骨架 |
| 测试脚本 | **51 个 `scripts/test-*.mjs` + 26 个 `scripts/test/*.mjs`** | 单测 + 静态守卫 + 浏览器 E2E |
| 文档 | **38 份 `docs/*.md`** | 每版计划、设计约束、实测数据 |

首屏包（v17.0.0，README 记录）：**842,636 字节**；构建产物主 bundle **822.9 KB**，另有 40+ 个按需 chunk；Stockfish 的 `engine-src.js` 约 2.3 MB，Maia 每档约 2.2 MB。

**验证情况**：我在当前 orb（Linux，Node 26）跑了 `npm run test:static`，全部通过（25 个测试域，覆盖规则、内容、持久化、源码守卫等）。这说明**大部分 JS 模块与平台无关、可独立运行**；但浏览器 E2E（Playwright/Chromium+WebKit）和引擎实测没有跑，桌面壳的编译也没验证——本机没有 Zig 0.16 和 `@native-sdk/cli`，`zig build` / `native package` 跑不了。这一点在评估里必须如实标出。

### 1.3 两个仓库的互补性

| | **chessboard** | **goban（五子棋）** | 围棋需要 |
|---|---|---|---|
| 许可 | **GPLv3**（因 Stockfish/Maia） | **MIT** | 取决于复用哪一份 |
| 原生壳 | 成熟：main/runner/bridge/dialogs/menus/chrome/sync，6.5k 行 | 同架构，较简（855 行 Zig） | chessboard |
| 棋盘 | 8×8 方格 + 棋子精灵 | **15×15 交叉点 + 圆子 + 阴影 + 四主题** | goban 更接近 |
| 规则 | chess.js 0.13.4 + fide.js | 五子棋连五，无提子 | 全新（Sabaki 库） |
| 棋谱 | PGN + 棋谱树 + 开局库 | **SGF 基础**（15 路，只读主线） | SGF FF[4] 全量 |
| 引擎 | Stockfish wasm + Maia 人类网络，21 档 | 自研 C3 五子棋引擎，四档 | KataGo |
| 产品系统 | **课程/谜题/残局/名局/棋谱库/复盘/成就/进度/每日/三语** | 对局库、复盘、练习、每日、错题本、中英 | chessboard 更全 |
| 测试 | 51 脚本 + 26 模块 + 双浏览器 E2E | 少量 | chessboard |
| 体量 | 10.5 万行 JS | 1.2 万行 JS | 取两者之长 |

**结论**：围棋 App 的最佳供体不是单一仓库，而是 **chessboard 的壳与产品系统 + goban 的棋盘几何与石子手感**。

### 1.4 证据等级与置信度

这份评估把“实测”“外部资料”“工程判断”分开，避免把估算当成事实：

| 结论 | 证据 | 置信度 |
|---|---|---|
| 这套架构已跨棋种复用成功 | v0.1.0 提交信息、v0.4.0「去围棋化」、goban/chessboard 代码对照 | **高** |
| JS 平台层可独立运行 | `npm run test:static` 25 个测试域全绿（本机实测） | **高**（不含 E2E/桌面壳） |
| 代码复用约 30% / 改造 25% / 新写 45% | 按文件归类与行数统计，非逐函数审计 | **中**（工程判断） |
| 内容占 58%、四语新增约 3,450 条 | 文件行数、i18n 字典与内容表的字符串计数（本机实测） | **高**（计数）/ **中**（翻译工期） |
| 围棋规则/SGF 有成熟 MIT 库 | `@sabaki/go-board`、`@sabaki/sgf` 安装并跑通 19×19 与变着解析（本机实测） | **高** |
| KataGo 可嵌入 | 第三方 WASM spike（b6c96 约 148 v/s 9 路；Safari M2 约 125 v/s）；**未在真实 WKWebView/WebView2 实测** | **中低**，必须 P0 |
| KataGo 原生子进程可行 | KataGo 官方 GTP/analysis、Metal/Eigen 后端；**打包/签名/进程生命周期未验证** | **中高** |

| 四语本地化 10–12 人周 | 字符串量实测；译者产能与母语审校按行业经验估算 | **中** |
| 桌面壳可编译、可打包 | **未验证**：本机没有 Zig 0.16 / Native SDK | **未验证** |

**结论的边界**：这是一份“能不能做、怎么起步”的评估，不是“三个月一定上线”的承诺。真正需要先用代码回答的只有两件事：KataGo 在真实 WebView 里的性能，以及四语/围棋术语的母语审校质量。其余（壳、存档、棋谱库、复盘、训练框架）都有现成代码与测试可依。

评分是工程判断，不是精确行数比例；“复用度”指**代码/结构可直接保留的程度**。

| 层 | 现有实现 | 围棋处置 | 复用度 |

### 2.1 按工作量粗算

| 类别 | 占比 | 说明 |
|---|---:|---|
| 直接复用 | **30–35%** | 壳、桥、存档、棋谱库、UI、i18n 基础设施、构建/测试 |
| 改造复用 | **20–25%** | 复盘、训练、棋谱树、音频、统计、引擎调度 |
| 新写代码 | **40–45%** | 围棋规则/数目、棋盘、SGF 适配、KataGo、复盘指标 |
| 新做内容 | **另计，约总工作量 50%** | 课程、题库、定式、名局、翻译、验证 |

**这解释了为什么“复用 chessboard”不等于“三个月做完”：代码可以抄，内容抄不了。**

## 3. 围棋带来的七个结构性差异

### 3.1 棋盘几何：从 8×8 方格到 19×19 交叉点

- 落子在**交叉点**，不是格子；361 个命中目标。
- 坐标：A–T **跳过 I**，行号从下往上；SGF 坐标从左上角起。两套坐标系的换算是经典 bug 源，必须单测。
- 星位随路数变化：9 路 5 个、13 路 5 个、19 路 9 个。
- 没有“棋子精灵按类型分六种”，只有黑白圆子；但需要：最后一手标记、手数、提子数、劫、禁着点、领地/ownership 热图、变着标记、坐标。
- 19×19 在 520px 最小窗口下每个交叉点约 25px，触摸/鼠标命中要重新设计。

**复用影响**：chessboard 的 `board.js` 只能提供命中测试、动画、主题 token 的模式；**goban 的 `draw.js` 才是可直接改造的起点**（15×15 交叉点、圆子、阴影、四主题、最后一手、悬停预览、胜利线）。

### 3.2 规则：几乎没有重叠

| 国际象棋 | 围棋 |
|---|---|
| 将军/将死/逼和 | 提子/气/禁着点/劫/超级劫 |
| 王车易位/吃过路兵/升变 | 让子/贴目/数目 |
| 50 回合/三次重复 | 打劫/循环/终局协商 |
| 子力价值 | 领地/模样/厚薄/官子 |

`chess.js` + `fide.js` 一行都用不上。建议：

- **合法性/提子/简单劫/禁着**：`@sabaki/go-board`（MIT，40 KB，`makeMove`/`analyzeMove`/`getLiberties`/`getRelatedChains`）。
- **超级劫/循环**：在棋谱树层做局面哈希（`@sabaki/go-board` 的 `_koInfo` 只处理简单劫）。
- **数目**：自己写日本规则（领地+提子+贴目），并用 50–100 局已知结果的 SGF 做回归。
- **死子判定**：`@sabaki/deadstones`（Monte Carlo）+ 用户手动标记 + KataGo ownership 建议。

维护性注：`@sabaki/go-board` 1.4.3 停在 2022 年，API 很小、稳定，但不再更新；`@sabaki/sgf` 3.5.0（2026-07）仍在维护。若担心长期风险，把 go-board fork 进仓库（MIT 允许）并用自己的围棋回归测试锁住行为，而不是依赖上游发版。

这是**必须做对**的部分：规则错一次，用户就不信任整个 App。

### 3.3 棋谱格式：SGF，不是 PGN

- 围棋用 SGF FF[4]：`GM[1]`、`SZ[19]`、`KM[6.5]`、`HA[2]`、`RU[Japanese]`、变着树、`C[]` 注释、`AB/AW` 摆子、`TR/SQ/CR/LB` 标记。
- chessboard 的 PGN 解析器/棋谱树/开局库不能直接用；但 `game-tree.js` 的“节点 + 变着 + 当前路径”UI 模式可以复用。
- 推荐 `@sabaki/sgf`（MIT，135 KB，完整 tokenizer/parser/stringify，支持变着与压缩点）+ `@sabaki/immutable-gametree`（MIT，35 KB）。
- goban 的 `sgf.js` 只写/读 15 路主线，适合做“导出”起点，不适合做完整导入。

### 3.4 引擎：从 Stockfish 到 KataGo

这是全项目唯一的**硬风险**，单独在第 4 节展开。

### 3.5 复盘指标：从厘兵到胜率/目差

- 国际象棋：centipawn、ACPL、准确率、`?! ? ??` 阈值、开局库。
- 围棋：**胜率差**、**目差**、**ownership 热图**、**目数曲线**、**关键手**、**AI 推荐点**、**变化图**。
- KataGo 的 analysis 输出直接给 `winrate`、`scoreMean`、`scoreStdev`、`ownership`、`pv`、`visits`——比 Stockfish 的 UCI 信息更丰富。
- chessboard 的 `eval-graph.js`（评分曲线）、`moments.js`（关键时刻）、`panel.js`（解释卡片）、`lines.js`（变着）**结构可以直接改造**；阈值要重新标定（例如胜率掉 5/10/20 个百分点对应 `?! ? ??`）。
- “准确率 = 100 × e^(−平均失分/120)”这类公式不能照搬；围棋要用胜率损失或目差损失重新定义。

### 3.6 教学内容：完全不同的知识体系

- 围棋：吃子 → 死活 → 手筋 → 定式/布局 → 中盘 → 官子 → 名局。
- 题型：死活题（活/杀/劫）、手筋、布局选点、官子大小、形势判断。
- 判定：国际象棋战术题常有“唯一将死/唯一得子”的精确判定；围棋死活题需要**搜索/引擎验证**，因为“活”是多解问题。
- chessboard 的 `trainer/*` 框架（题目卡片、提示分级、错题本、SRS、每日 5 题、按等级抽题）可以复用；**题目本身、判定器、讲解文案**要重做。

### 3.7 UI 语义：没有“子力”，有“提子/贴目/领地”

- 顶部条：chessboard 是“谁走 + 时钟 + 子力差”；围棋是“谁走 + 提子数 + 贴目 + 目差”。
- 终局：chessboard 是将死/认输/和棋；围棋是双方 pass、点目、死子确认、数目结果。
- 侧栏：chessboard 是棋谱 + 评估 + 开局名；围棋是棋谱 + 胜率/目差 + 变化图 + ownership。
- 这些是 `app.js`/`game-end.js`/`material-strip.js` 的改造点，不是壳的改造点。

## 4. 引擎：唯一的硬风险

### 4.1 为什么不能沿用 Stockfish 方案

| | Stockfish（chessboard） | KataGo（围棋） |
|---|---|---|
| 算法 | Alpha-Beta + NNUE | MCTS + 深度神经网络 |
| 协议 | UCI | GTP / analysis JSON |
| wasm 体积 | 1.8 MB | 引擎 wasm 约数 MB + 模型 5–271 MB |
| 限强 | `UCI_LimitStrength` / `UCI_Elo`（1320–3500） | 无等价 Elo；用 visits / playoutDoublingAdvantage / rootNoise / humanSL |
| 输出 | cp、PV、depth、seldepth | winrate、scoreMean、ownership、PV、visits |
| 线程 | 单线程 lite 足够 | 多线程需要 SharedArrayBuffer（zero:// 不发 COOP/COEP） |

### 4.2 五种可选方案

| 方案 | 强度 | 体积 | 延迟 | 集成 | 平台 | 许可 | 风险 |
|---|---|---|---:|---|---|---|---|
| **原生 KataGo 子进程**（GTP/analysis） | 最强（b18/b28） | 98–271 MB 模型 + 二进制 | Metal/CPU 视机器 | 新写 Zig 子进程 + 异步桥 | macOS/Windows | MIT + 网络许可 | 中高：打包、签名、交叉编译、进程生命周期 |
| **KataGo WASM（Eigen）** | 中强（b6c96/b10c128） | 引擎数 MB + 模型约 5–12 MB | 约 148 visits/s（9 路，b6c96，第三方 spike）；Safari M2 约 125 v/s | 复用 Blob worker 模式 | 所有 WebView | MIT | 中：单线程、19 路慢、模型加载 |
| **ONNX Runtime Web + WebGPU** | 强（b18c384） | ORT wasm 约 10 MB + 模型 30–116 MB | 强 GPU 约 100 ms/pos（Kaya 实测）；WASM 约 165 ms/pos | 新写推理+MCTS | 需 WebGPU；WKWebView 旧版不支持 | MIT（ORT/模型） | 中高：WebGPU 可用性、内存 |
| **GNU Go WASM** | 弱（约 5k–10k） | 小 | 快 | 简单 | 所有 | GPLv3 | 低，但棋力不够撑产品 |
| **纯 JS MCTS + 棋型评估** | 9 路入门可接受，19 路弱 | 0 | 快 | 自研 | 所有 | 自有 | 低，但上限低 |

> 体积注：b18c384nbt 97,898,094 字节、b28c512nbt 271,440,852 字节为 HTTP Content-Length 实测；b6c96（约 103 万参数）与 b10c128（约 299 万参数）的 5/12 MB 是按参数量估算，P0 时以下载文件实际大小为准。

**关键架构约束**（来自 chessboard 的实现，必须正视）：

- `zero://` 下 **不能 fetch 打包文件、不能从 URL 加载 worker 脚本**；Stockfish 的 wasm 是以 base64 塞进 `engine-src.js` 经典脚本，再由 Blob worker 接收。
- CSP 只给了 `'wasm-unsafe-eval'`，没有 COOP/COEP，**没有 SharedArrayBuffer**，所以 KataGo WASM 只能单线程。
- 桥单帧上限 1 MiB、文件上限 16 MiB（全部数据 64 MiB）；大模型要走分块或原生侧读取，不能一次性 base64 过桥。

这意味着：

- **b6c96（约 5 MB）/ b10c128（约 12 MB）适合嵌入**，像 Stockfish 一样做成按需加载的经典脚本；
- **b18c384（97.9 MB）/ b28c512（271 MB）不适合嵌入**，应该走原生子进程或让用户单独下载模型；
- 如果坚持“全 WebView”，19 路强分析会受限；如果接受“原生 KataGo 子进程”，壳层要多写一个模块，但棋力和分析质量上一个台阶。

### 4.3 推荐（一个版本内定案）

**引擎方案必须在 v1.0 内一次定案，不能“先 WASM、后原生”拆成两个版本。** P0 用真实 WebView 数据二选一：

**方案 A：KataGo WASM Eigen + b6c96/b10c128（若 P0 达标）**

- Blob worker，单线程，首帧后懒加载；
- 覆盖 9/13/19 路 AI 对弈 + 提示 + 复盘；
- 档位：`maxVisits` 分档（如 30 / 80 / 200 / 600），加 root noise / 候选抽样做“入门/休闲”；
- 19 路分析必须达到 v1.0 的性能门槛，不能“先只做 9/13 路”。

**方案 B：原生 KataGo 子进程（若 WASM 不达标，或 19 路分析质量不够）**

- macOS Metal、Windows Eigen/OpenCL，GTP 或 analysis JSON，经异步桥接；
- 用于 19 路对弈、深度复盘、ownership、变化图；
- 模型按需下载或随安装包分发（b18c384 约 98 MB）；
- 新增 Zig 模块（进程管理、stdio、超时、重启、路径签发），但都是成熟工程；
- 这是同一个 v1.0 的一部分，不是“后续增强版”。

**兜底（只用于降级，不作为发布方案）**：

- 纯 JS MCTS 只做 9 路“入门档”/无引擎降级；
- GNU Go WASM 仅在“必须极小三平台”时考虑，GPLv3 且棋力有限。

**结论**：v1.0 必须同时具备 9/13/19 路、4–6 档、复盘/ownership；如果 WASM 只能做好 9/13 路，就选 B，不要用“先发 9/13 路”的版本拆分。

### 4.4 必须先过的闸门（Go/No-Go）

在真实 **WKWebView（macOS）** 和 **WebView2（Windows）** 里，不是 Chrome：

1. b6c96 在 19 路上达到 **≥ 100 visits/s**，或 9 路上 ≥ 150 visits/s；
2. 一次 200 visits 的落子 **≤ 2 s**（中端笔记本）；
3. 冷启动到引擎 ready **≤ 3 s**，内存峰值 **≤ 1.5 GB**；
4. 引擎初始化失败时有可读错误，不白屏；
5. 模型/引擎脚本能在 `zero://` + CSP 下加载（Blob worker + base64），不需要放宽 CSP。

任一条不达标：改用原生 KataGo 子进程；19 路属于 v1.0，不能缩成“只做 9/13 路”的版本。

## 5. 内容与产品

### 5.1 不要做“另一个 Sabaki”

围棋桌面端已经有：

- **Sabaki**（MIT，Electron，成熟 SGF 编辑器 + GTP 引擎）；
- **KaTrain**（KataGo 教学/复盘，强但技术向）；
- **Ogatak / q5Go / Lizzie**（分析型 GUI）；
- **Kaya**（AGPL，Tauri + React，功能非常完整，含拍照识谱）；
- 在线平台 OGS / Fox / Tygem。

如果做一个“通用 SGF 编辑器 + KataGo 分析器”，会正面撞上这些成熟免费产品。chessboard 的真正优势不是“能下棋”，而是**把零基础教学、每日练习、错题本、复盘解释做成一条闭环**。围棋 App 应该继承的是这个，而不是 Sabaki 的功能表。

### 5.2 建议的内容盘子（v1.0）

| 模块 | 数量 | 说明 |
|---|---:|---|
| 入门课程 | **60–120 课** | 从“气/提子/禁着”到“两眼活棋/劫/官子”；每课 1 个局面 + 1 个任务 + 1 句讲解 |
| 死活题 | **300–500 题** | 9 路/13 路为主，按难度分档；答案用 KataGo 验证，多解要接受 |
| 手筋/布局 | **50–100 个** | 定式/布局选点，配 2–3 句“为什么” |
| 名局 | **20–40 局** | 公版/授权棋谱，带关键手注释 |
| 每日挑战 | **5 题/天** | 复用 chessboard 的 date-seeded + 到期优先 |
| 错题本 | 自动 | 从自己的对局/练习派生，SRS 1/3/7/21 天 |
| 复盘 | 每局 | 胜率曲线 + 关键手 + ownership + “从这一手重下” |

### 5.3 内容许可（比代码更容易踩坑）

- **课程/讲解**：自己写，或明确授权的教材；不要抄《死活大全》《定式辞典》等版权作品。
- **死活题**：优先 CC0/公版/自研 AI 生成 + 人工验证；Cho Chikun 等题库有版权。
- **名局棋谱**：棋谱本身的版权因司法辖区而异；优先使用明确开放的数据集（如 GoGoD 的授权条款、OGS 公开棋谱、自己下的棋）。
- **KataGo 模型**：KataGo 代码 MIT；官方网络在 `katagotraining.org/network_license` 下允许商用/再分发（需保留声明）。b6c96/b10c128 属 g170 运行，部分为 CC0。
- **Sabaki 库**：MIT，可直接用，保留版权头。
- **chessboard 代码**：GPLv3。如果新 App 要闭源，不能直接复制 GPL 代码；只有当仓库版权全部在你手里（提交记录主要是你与 AI 代理）时，才可以对自己写的部分重新许可。第三方部分（chess.js BSD、Stockfish/Maia GPL、棋子图形 GPL/CC）在围棋 App 里本来就不会用到。**建议在开工前把“哪些文件是谁写的、能否重许可”列一张清单**；如果不确定，就用 **goban（MIT）** 作为壳的起点，再从 chessboard 移植思路而不是文件。

### 5.4 差异化

- **零基础友好**：9 路起步、每课一个可完成的小目标、复盘说人话（“这一步让这块棋只剩一口气”）。
- **每日 10 分钟**：5 道题 + 1 课 + 1 盘 9 路，连续打卡。
- **自己的错题**：从你的对局里挖“漏看的气/没补的断/错误的劫”，进错题本。
- **本地优先**：离线、无账号、无网络请求；SGF 可与 OGS/Fox/Tygem 互通。
- **原生质感**：macOS/Windows 原生壳、木盘、石子声、无 Electron 的启动等待。

## 6. 三条路线对比

| 路线 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. Fork chessboard** | 复制 chessboard，删棋种内容，换棋盘/规则/引擎 | 最快得到成熟壳、测试、存档、棋谱库、复盘、设计系统 | GPLv3；`app.js` 棋种耦合深；要删 58% 内容；19 路棋盘要新写 | 你拥有版权、接受 GPL、追求最快 |
| **B. Fork goban + 移植 chessboard 系统** | 以 MIT 的 goban 为壳，移植 chessboard 的 persist/library/review/trainer/UI | 许可干净；棋盘/石子/SGF 已接近围棋；代码量小 | 要移植大量系统；goban 的 UI/测试不如 chessboard 成熟 | 要闭源/商用，或想从干净底座开始 |
| **C. 新仓 + Sabaki 库 + 参考 Kaya** | 全新前端，规则/SGF 用 Sabaki MIT 库，Kaya 只做功能参考 | 架构最干净；许可最可控 | 最慢；要重写壳/存档/棋谱库/复盘 | 团队有充足时间、想长期维护 |

**推荐**：

- 如果**不考虑闭源**：走 **A**，但不要改 `app.js`，而是新写一个围棋 `app.js`，从 chessboard 导入可复用模块；用 goban 的 `draw.js` 做棋盘；用 Sabaki 库做规则/SGF。
- 如果**要考虑闭源/商用**：走 **B**，以 goban（MIT）为壳，移植 chessboard 的 `persist.js`、`library-*`、`review/*`、`trainer/*`、`styles.css` 的思路与结构（不是逐行复制），并保留 MIT 声明。
- **C 不作为第一步**；它适合在 A/B 验证产品后，再逐步重构。

无论 A/B，都建议**新开仓库**（`goban-studio`），不要在原仓库上原地改造。原因：chessboard 的 17 个版本、38 份文档、51 个测试脚本都以国际象棋为前提；原地改造会让两边都难以维护。

## 7. 单版本完整产品化：工作流与估算

**前提（按你的要求）**：**不拆公开版本，不先发 MVP**。P0–P5 是内部工作流/里程碑，唯一的发布是 **v1.0 完整产品**；内容、四语、QA 必须在发布前全部完成。内部可以有 50 人封闭测试，但那是同一版本的验收，不是另一个版本。

### 7.1 v1.0 必须完成的范围

| 模块 | v1.0 的最低完整范围 |
|---|---|
| **对弈** | 9/13/19 路；日本规则；贴目/让子；读秒；pass/resign；悔棋/提示；双人同屏 |
| **AI** | KataGo 4–6 档；9/13/19；分析/提示；入门 human-like；真实 WebView 性能达标 |
| **复盘** | 胜率/目差曲线；关键手；ownership；变着；从这一手重下；分析保存 |
| **棋谱** | SGF FF[4] 导入导出；棋谱库 1 万局；搜索/标签；备份/恢复 |
| **教学** | 60 课；300 道死活题；40 个定式/布局；20 局名局；每日/错题/SRS/成就 |
| **四语** | 中/英/韩/日；UI + 全部教学内容；母语审校 |
| **平台** | macOS/Windows；签名/公证；安装包；更新检查；a11y；键盘；主题/音效 |

如果目标提高到 **120 课 / 500 题 / 40 名局 / 80 定式**，再加 **12–20 人周**、日历 **+2–3 个月**。这份评估按上表的 60/300/40/20 计算；你可以把“完整”定得更高，但工期要同步加。

> 说明：四语翻译的字符串量目前按 chessboard 的 2,019 条/语言类比；围棋课程/题库写完后才能精确。翻译工期应按实际字数校准，不能按条数拍脑袋——这是本评估里不确定性最大的一项。

### 7.2 工作流与工期

| 工作流 | 范围 | 人周 | 日历（并行） |
|---|---|---:|---|
| **P0 技术 Spike** | 19 路棋盘 + 规则 + SGF 往返 + KataGo 真机 200 visits | 1–2 | 第 1 周 |
| **代码地基** | 新仓、壳、棋盘、规则、本地双人、存档、四主题、四语 i18n | 8–10 | 第 2–11 周 |
| **引擎/复盘** | KataGo、档位、提示、胜率/目差、ownership、数目、棋钟 | 10–12 | 第 4–15 周 |
| **内容** | 60 课、300 死活题、40 定式/布局、20 名局、每日/错题/SRS | 18–24 | 第 1–24 周 |
| **本地化** | UI + 全部内容，中/英/韩/日，母语审校 | 10–12 | 第 12–26 周 |
| **打磨/QA** | a11y、引导、打包、签名/公证、50 人封闭测试、四语布局回归 | 8–10 | 第 24–34 周 |
| **发布** | 发布说明、网站、许可/隐私、支持 | 2 | 第 35–36 周 |
| **合计** | 一个完整 v1.0 | **57–72 人周** | **32–36 周（3–4 人，部分兼职）** |

**人力假设**：1 名全职开发者（壳/棋盘/规则/KataGo/复盘/打包）、1 名全职围棋内容作者（课程/题库/名局/定式 + 验证）、2 名兼职翻译/母语审校（中英韩日）、1 名兼职设计/QA。开发者不是唯一瓶颈；**内容和本地化是 critical path**。

**单人 + AI 辅助**：**13–17 个月**；四语仍需外聘母语审校，不能只靠机翻。若没有内容作者，只有开发者，产品化不成立——课程和题库不是“写几段文案”，是逐题验证的棋。

**与上一版的差异**：上一版按“首发 30 课 + 150 题 + 后续追加”估 22–34 人周（5.5–8 个月）。按“一个版本彻底完成”，工作量是 **57–72 人周（8–9 个月，3–4 人）**；这不是保守，而是把内容、四语、QA 全部放进同一个发布门槛。

**与 chessboard 的历史对照**：chessboard 从 v0.1.0（2026-07-22）到 v17.0.0（2026-10-31）约 3 个月，但那是高强度迭代 + 大量内容逐步补齐 + 17 个版本；它不是一个“首发即完整”的产品。围棋要一次完成，不能按 3 个月排期。

## 9. 最终建议

### 9.1 做，但先做一个 1 周的 P0 Spike

**Spike 范围（只证明风险，不追求产品）**：

1. 19×19 Canvas 棋盘（复用 goban `draw.js` 的交叉点画法），能落子、提子、显示最后一手；
2. `@sabaki/go-board` 规则 + 简单劫/禁着 + 一局完整对弈；
3. `@sabaki/sgf` 导入/导出，含 2 个变着；
4. KataGo WASM b6c96 在 Blob worker 里跑 200 visits，返回一个着法；
5. 在 **真实 WKWebView + WebView2** 里跑通，记录冷启动、visits/s、内存；
6. 用 10 局已知结果的 SGF 跑数目，全部正确。

**通过标准**：第 4 条 ≤ 2 s/手、第 5 条不崩、第 6 条 10/10 正确。
**不通过**：改原生 KataGo 子进程；不能缩到 9/13 路——19 路属于 v1.0。

### 9.2 不要做的事

- 不要把 chessboard 的 `app.js` 直接改成围棋；
- 不要复用 `chess.js`/`fide.js`/PGN/ECO/Stockfish/Maia；
- 不要用“先 9/13 路、19 路以后再说”的版本拆分；19 路属于 v1.0，9/13 路只是内部验证；
- 不要拆公开版本；P0–P5 是内部工作流，唯一发布是完整 v1.0；
- 不要首发就做 iOS/Android；
- 不要做“另一个通用 SGF 编辑器”；
- 不要在没有内容授权清单的情况下开始写课程/题库。

### 9.3 一句话

**chessboard 的壳和产品系统可以直接拿来用，围棋的规则/引擎/内容必须重做；这不是“能不能复用”的问题，而是“复用哪 30%、重做哪 70%”的问题。** 先花一周验证 KataGo 在真实 WebView 里的表现，再在同一个 v1.0 内定案 WASM 还是原生子进程；这个决定做完，剩下的就是内容、四语与 QA 的产品化工程。

## 10. 命名与四语：追加评估

### 10.1 仓库名：`goban-studio`

**结论：在不改现有 `goban` 的前提下，新仓库叫 `goban-studio`（产品名 `Goban Studio`）。**

理由：

- 在 `goban` 名字上加 `studio`，表达“完整的围棋工作室”：下棋、复盘、学习、棋谱库都在里面；不是单一功能（kifu/tsumego），也不是一个通用词（goban）。
- 与现有五子棋 `Goban` 区分：老仓库/老应用保持 `goban`、`Goban.app`、`dev.hxddh.goban` 不动；新应用 `Goban Studio.app`、`dev.hxddh.gobanstudio`。两个应用可以并排安装，不抢 Bundle ID，不抢更新源。
- `hxddh/goban-studio` 已查 404，可用；不需要 GitHub 改名，不会触发旧链接/Release/Issue 重定向问题，也不会让五子棋的更新源指向新应用。
- 四语：品牌 `Goban Studio` 不翻译；副标题写「围棋 / Go / 바둑 / 囲碁」。中文描述可用「围棋工作室」，但品牌保留英文。

候选对比：

| 名字 | 含义 | 适合 | 判断 |
|---|---|---|---|
| **`goban-studio`** | 围棋工作室 | 完整产品（下棋/复盘/学习/棋谱） | **首选**；与 `goban` 有品牌连续性，又不冲突 |

### 10.2 四语不是“加一个字典”

先分清两个范围，成本差三倍：

- **界面四语**：1,431 个 UI 键 + 字体/排版 + 测试，约 **1–2 周**。
- **教学内容也四语**：课程、死活题、名局、开局每语言 2,019 条，再加 **3–8 周**（取决于 AI 初翻 + 母语审校，还是专业翻译）。

本评估按“教学内容也四语”估算；如果你只要求界面四语，本地化从 10–12 人周降到 2–3 人周，总工作量可减 7–10 人周。

chessboard 目前是 **zh-CN / en / ja 三语**，1,431 个 UI 键。四语（中/英/韩/日）的真实账：

| 项 | 三语现状 | 四语目标 | 韩语增量 |
|---|---:|---:|---:|
| UI 键 | 1,431 | 1,431 | +1,431 条 |
| UI 字符串（键 × 语言） | 4,293 | **5,724** | +1,431 |
| 教学内容（每语言） | 2,019 条 | 2,019 条 | +2,019 条 |
| 内容字符串（源 + 3 译） | 6,057 | **8,076** | +2,019 |
| 合计字符串 | 10,350 | **13,800** | **+3,450** |
| 约合字符量 | — | — | **约 18 万字符** |

内容 2,019 条的构成（实测，每语言）：课程 889、进阶课程 266、名局 111、更多名局 273、开局 291、谜题 189。韩语不是“把英文再翻一遍”——围棋术语必须用韩国棋院/韩国玩家的说法（바둑、활로、패、사활、정석、포석、끝내기、덤、접바둑），否则一眼就是机翻。

**架构上已经准备好的部分**：

- 语义化 key，不是编号；`data-i18n` / `t()` / `tf()`；未知 key 回退到中文，不会白屏。
- 内容按 `id × locale` 拆表：`lessons-ko.js` 只放文字，局面/解法仍在 `lessons.js`，翻译不会改棋。
- 语言按需 chunk：`chunk-lang-ko.js` 可以在首帧前加载（保存的语言），也可以懒加载；不影响首屏包。
- 构建期守卫：键完整、无重复、无未使用键、非中文表不得残留中文、内容表覆盖率。

**架构上还没准备好的部分**（这些是加韩语真正的工程量）：

1. `src/web/js/lang-ids.js` 的 `LANG_IDS` / `LANG_NAMES` / `detectLang` 是硬编码三语；要加 `ko` 和 `한국어`，并让 `ko-KR` 命中。
2. `scripts/bundle.mjs` 的 `CHUNKS` 只有 `chunk-lang-en` / `chunk-lang-ja`；要加 `lang-ko.js` → `chunk-lang-ko.js`，以及 6 个内容 `*-ko.js`。
3. `chunk-boot.js` 是构建产物，里面的 `LANG_IDS` 与 `LANG_CHUNKS` 是从源码生成的；生成脚本与 `sync-dist.mjs` 要同步。
4. `scripts/test/i18n-ui.mjs` 有多处硬编码 `["zh-CN","en","ja"]`：重复键检查、F4 句子回归、v15 命名一致性、语言循环。加 `ko` 要么改成读 `LANG_IDS`，要么补第四列。
5. `scripts/test/lang.mjs` 的 `untranslated()` 对非日语只检查“没有汉字”；韩语没有汉字，**英文文本也会通过**。必须加 `hangul` 检测和 `hangulRatio` 语料检查（类似现有的 `kanaRatio`），否则韩语表可以整段是英文而测试全绿。
6. `scripts/measure-boot.mjs`、`test-content-e2e.mjs`、`test-endgames-e2e.mjs`、`test-review-e2e.mjs`、`test-learning.mjs`、`test-shell-e2e.mjs` 等 20+ 处三语循环；要加 `ko` 或改成遍历 `LANG_IDS`。
7. `styles.css` 没有 `html:lang(ko)` 字体栈；要加 macOS `Apple SD Gothic Neo`、Windows `Malgun Gothic`、Linux `Noto Sans KR` / `Noto Sans CJK KR`。韩语要 `word-break: keep-all`（避免单词中间断行）；日语可加 `line-break: strict`。韩语用拉丁标点，不需要中日那套 `CJK Punct` 字体。
8. 截图与布局回归目前是“四种宽度 × 主题 × 三语”；加韩语意味着多 33% 的截图，且韩语标签长度与中文/日文不同，按钮不折行、不截断要重新验。
9. README、`docs/measured.json`、发布说明里的“1431 个界面键三语”要改成四语；`test-chess.mjs` 的键数断言虽然动态读取，但文档数字要对上。

**翻译与审校成本**：

- UI 1,431 条：专业翻译 5–8 个工作日，母语审校 2–3 个工作日；加布局回归 2–3 个工作日。
- 内容 2,019 条（约 16 万中文字符）：专业围棋译者 4–8 周；AI 初翻 + 母语棋手审校 3–5 周。**这是韩语的主要成本，不是代码。**
- 术语一致性：先锁定一份四语术语表（见 §10.3），所有翻译按表走；测试扫描禁用词/变体。机翻最容易把「气」翻成 energy、「劫」翻成 disaster、「手筋」翻成 tendon——这类错误会直接毁掉教学可信度。

**四语工作流（不拆版本）**：

- **P1 就把四语地基做好**：`LANG_IDS`、字体栈、`lang-ko` chunk、四语布局测试、术语表。代码量不大（约 3–5 天），但能避免后期返工。
- **P4 全量翻译**：60 课 + 300 道死活题 + 40 个定式/布局 + 20 局名局 + 全部 UI，四语一次做完；因为不拆版本，不能留到“后续版本”。
- **P5 做四语验收**：四语 × 四宽度 × 两主题截图，母语棋手走查，术语表一致性测试。

### 10.4 四语验收门槛

1. **键完整**：1,431 个 UI 键在 zh-CN / en / ko / ja 四份字典里都存在，无重复、无未使用键（现有测试扩展为四语）。
2. **内容覆盖**：v1.0 全部 60 课 + 300 题 + 40 个定式/布局 + 20 局名局 + 全部 UI 的 id 在四语表里 100% 覆盖；缺一条不得发布。
3. **不是机翻**：韩语表必须通过 `hangulRatio`（例如 ≥ 0.6 的字符串含韩文）与术语表扫描；英语表不得残留汉字；日语表不得整段等于中文原文。
4. **首帧语言**：保存的语言在首帧就是该语言（现有 `chunk-boot.js` 机制）；四语各测一次冷启动。
5. **布局**：四语 × 四种宽度（520 / 640 / 900 / 1400）× 深/浅主题；按钮不折行、不截断，韩语 `keep-all` 生效，日语禁则生效。
6. **字体**：macOS（Apple SD Gothic Neo / Hiragino）与 Windows（Malgun Gothic / Yu Gothic）各走查一次；韩文不能落到中文字体上。
7. **母语审校**：至少一位韩语围棋玩家 + 一位日语围棋玩家逐条审术语与语气；机翻只能做初稿。
8. **术语一致性**：同一概念在 UI、课程、复盘、题库里用同一个词；测试扫描 `glossary.json` 的禁用变体。

### 10.5 对总评估的影响

- 四语在单版本里不是“加 3–5 周”，而是 **10–12 人周的本地化工作流**（UI + 全部内容 + 母语审校），与内容生产并行；总工作量见 §7 的 **57–72 人周**。
- 韩语全量内容 2,019 条约 **3–5 周（AI 初翻 + 母语审校）** 或 **4–8 周（专业翻译）**；因为不拆版本，这部分必须进 v1.0，不能留到 v1.1。
- 如果只要求界面四语、教学内容只用中文/英文，本地化工作流可降到 **2–3 人周**；但按你的要求（四语应用），本评估按全量四语计算。
- 四语也是差异化：韩国、日本是围棋成熟市场，中文是发源地，英文是国际社区；一个四语、离线、入门优先的原生 App，比只做英文的 SGF 编辑器更有位置。但**翻译质量是信任问题**：术语错一次，棋手就不会再用它教孩子。

### 11.2 质量门槛

- [ ] 50 人封闭测试（不是公开 MVP）；发布时 0 个 P0/P1。
- [ ] 100 局对局无崩溃；19×19 渲染 60fps；引擎一手 ≤2s；冷启动 ≤3s。
- [ ] 数目 100 局已知结果 SGF 全对；复盘在 20 局上人工抽检通过。
- [ ] SGF 往返 100 份文件（含变着/让子/贴目/标记）无丢失。
- [ ] 四语 × 四宽度 × 深浅主题：按钮不折行、不截断；韩语 `keep-all`、日语禁则生效。
- [ ] 每课可完成、每题答案经 KataGo + 人工验证；不接受“多解但不判定”的题。
- [ ] 术语一致性：`docs/glossary.json` 扫描通过；无同一概念三种叫法。

### 11.3 发布门槛

- [ ] macOS Developer ID 签名 + 公证；Windows 代码签名；安装包；下载页；校验和。
- [ ] 更新检查可用；崩溃日志可导出；支持邮箱；隐私政策（离线、无账号、无遥测）。
- [ ] 许可：chessboard/goban 的自有代码、Sabaki MIT、KataGo MIT + 网络许可、字体 OFL、图标/音效逐项列清。
- [ ] 文档：用户手册、快捷键、FAQ、已知问题、发布说明；四语版本。
- [ ] 回滚方案：发布前保留上一版安装包与数据迁移路径；数据 schema 有版本号。

### 11.4 明确不做

- [ ] 不先发“缺内容的 MVP”再补；50 人封闭测试是同一版本的验收。
- [ ] 不说“19 路/四语/课程后续版本再加”；它们属于 v1.0。
- [ ] 不在 v1.0 同时做移动端；桌面先完成，移动端另立项目。
- [ ] 不用机翻直接上线；母语审校是发布门槛。
