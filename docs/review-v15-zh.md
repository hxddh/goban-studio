# Goban Studio v15.0.0 发布后评估与 v16 规划

评估日期：2026-11-14 · 对象：`main` @ `67bc99a`（v15.0.0，已发布）· 依据：v15 的执行记录（`docs/review-v14-zh.md` 附录）、四次发布演练和正式发布的 CI 日志、发布包内容核对、浏览器逐屏走查（中文浅色 1440×900、深色 1200×800）、代码体量统计。

## 0. 结论

v15 把 v14 评审里**能在代码里做完的事基本做完了**。棋盘、对局反馈、界面和工程质量这四块都有实质提升，发布流程也第一次在真实的 macOS / Windows 构建机上把 Metal 和 AVX2 引擎打进了包里。

剩下的问题换了性质：**不再是“代码里缺什么”，而是“没有在真实环境里验证过什么”**。

| 类别 | 现状 |
| --- | --- |
| 在 CI 里能验证的 | 基本都验证了：测试 604 项（单元）+ 146 项（界面）+ 84 项（原生），三个平台的打包都能启动引擎并通过自检 |
| 只有真机能验证的 | 都还没验证：Metal / AVX2 的实际速度、断电后存档是否完好、macOS 标题栏跟随深浅色、Windows 上的写入直通 |
| 只有人能判断的 | 都还没判断：落子声、每手评价的阈值是否合适、中韩日文案、新棋盘在真实屏幕上的观感、可用性 |
| 只有仓库所有者能做的 | 都还没做：代码签名、更新签名密钥、Windows 安装程序 |

**建议：v16 定为“验证版”。** 先把 v15 新加的东西在真机和真人身上验证一遍，按结果调；同时补上内容短板（名局讲解、高段题目）。只做一项新功能：一个能让人看清“引擎在用哪个后端、多快”的诊断页，因为后面所有的速度验证都要靠它。

---

## 1. v15 实际交付了什么（已核对）

- **发布**：v15.0.0 已公开发布，6 个安装包和 `SHA256SUMS` 齐全。我下载了 Apple Silicon 与 Windows 两个 zip，校验和一致。
  - Mac 包里同时有 `katago-metal`（11.7 MB）和 `katago`（Eigen，8.1 MB），以及 protobuf / abseil / katagocoreml 的许可文件。
  - Windows 包里同时有 `katago-avx2.exe` 和 `katago.exe`。
- **打包后自检**（CI 虚拟机上真实运行）：三个平台的 KataGo 都能启动、下棋、取消请求；拟人网络和新的强网络（kata1-b18c384nbt）都完成了下载、续传、校验和对局。
- **走查**：浏览器预览下所有页面没有报错。新棋盘、单元缩略图、两栏布局、今天页的一周进度都正常显示。

**v15 发布过程中暴露的问题**（都已修好，但说明流程有漏洞）：

| 问题 | 为什么到发布时才发现 |
| --- | --- |
| 存档测试在 Windows 上编译不过 | PR 的 CI 只在 Linux 上跑原生测试；改了原生代码后，Windows / macOS 的检查才会被触发 |
| protobuf 关掉 upb 后编不出 `protoc` | Metal 依赖的构建只在发布流程里跑 |
| Metal 版被编成要求 macOS 15 | 同上 |
| 自检的计时条件在虚拟 GPU 上误报 | 同上 |

四次演练、每次约 20–40 分钟才把这些问题依次暴露出来。**PR 阶段没有覆盖打包这条路径，是 v16 要先补的漏洞。**

## 2. 遗留问题（按类别）

### 2.1 需要真机验证（v15 新增、没在真机跑过）

| # | 项目 | 风险 | 怎么验证 |
| --- | --- | --- | --- |
| V1 | Metal 后端的实际速度和稳定性（Apple Silicon） | CI 上虚拟 GPU 第二次搜索比第一次慢 5 倍，真机上是否也有抖动未知；CoreML 首次编译模型可能有几秒卡顿 | 在 M 系列 Mac 上跑 `katago benchmark`，对比 Eigen；对局里测每手耗时 |
| V2 | AVX2 版的选择和回退（Windows） | CPU 检测或回退写错，就会一直用慢的版本，或直接起不来 | 在支持和不支持 AVX2 的两台 PC 上各开一局 |
| V3 | 断电后存档完好（N9） | macOS 的 `F_FULLFSYNC` 和 Windows 的写入直通只编译过，没真正运行过 | 真机上反复“保存后立即断电”，或用虚拟机强制关机 |

| V5 | 新强网络的速度 | 网络比原来大约 5 倍；Eigen 后端下可能过慢，“最强一档”对手可能要等很久 | 校准流程（calibrate.yml）重新测；必要时调整 `STRONG_VISIT_SCALE` |

## 3. v16 规划（建议）

**主题：验证版。** 把 v15 新加的东西在真机和真人身上验证一遍，按结果调；补内容；把发布流程的漏洞堵上。

### 3.1 先做（能在仓库里完成的）

| 顺序 | 内容 | 衡量 |
| --- | --- | --- |
| 1 | **PR 阶段覆盖打包路径**：改了 `src/*.zig`、`build.zig`、`engine/**` 或构建工作流时，PR 自动跑 macOS arm64 和 Windows 的完整打包与自检（只构建不发布），让 Metal 依赖这类问题在 PR 里就暴露 | v15 那四个问题，放在 PR 里都会失败 |
| 2 | **引擎诊断页**（设置 → 引擎）：显示当前用的是哪个构建（Metal / AVX2 / Eigen）、网络、每秒访问数；加一个“测速”按钮（调用 KataGo 自带的 benchmark）；回退时说明原因 | 用户和开发者都能看清引擎状态，V1、V2、V5 的验证都靠它 |
| 3 | **用新网络重建布局库**（C4），补上中国流 | book.yml 跑完；布局探索里能找到 Q16–Q3–R9 |
| 4 | **重新校准最强一档**（V5） | calibrate.yml 跑完，`docs/strength.md` 更新 |
| 5 | **题目首次随机执黑或执白**（C3） | 求解器已经支持颜色变换，只是首次固定为黑 |
| 6 | **名局讲解补齐**（C1）：15 局各补 3–5 个看点，由 KataGo 找出关键手、人工写说明 | 20 局都有至少 3 个看点 |
| 7 | **工程收尾**：根治布局探索检查的偶发超时；拆分 `net.zig`；复盘页按分析进度单独订阅；升级 setup-zig；评估 Playwright 1.65 | 全部测试连跑 10 次无偶发失败 |

### 3.2 需要真机或真人（这些不靠我能完成）

| 内容 | 谁来做 |
| --- | --- |
| V1–V4 真机验证 | 有 M 系列 Mac 和 Windows PC 的人，按 `docs/QA.md` 加一份“v15 新功能”清单逐项做 |
| H1 落子声、H2 评价阈值 | 一位下棋的人试用一周后反馈 |
| H3 文案审校、H4 内容复核 | 三位母语者、一位有段位的棋手 |
| H5 可用性测试 | 5 位新手，按 `docs/usability.md` 的协议 |
| O1–O4 签名与安装程序 | 仓库所有者申请证书和账号；拿到后我来接进工作流 |

### 3.3 段位题（C2）

题库扩到段位需要可靠的题源和强棋手审核，工作量大。建议单独立项，不放进 v16 的发布门槛。

### 3.4 不做

- **换默认的 b6c96 网络**：要重新校准所有难度，等 v16 的诊断页拿到真机速度数据后再定。
- **求解器移到 Worker**：v15 已测过，最慢约 230 ms，收益不够。
- **Zig 0.17**：Native SDK 仍只接受 0.16。

## 4. 发布前的门槛（v16）

1. PR 阶段的打包检查通过（§3.1 第 1 项），这是新增的门槛。
2. 发布演练一次通过。
3. §2.1 的 V1–V4 至少各有一台真机的验证记录，写进发布说明的“已知限制”或删掉对应条目。
4. PR #22 的修复在内。
